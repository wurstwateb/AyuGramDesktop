# TypendruckerGram Sync — дизайн

Дата: 2026-10-31
Статус: согласован, ждёт ревью спеки

## Цель

TypendruckerGram сохраняет удалённые сообщения и все версии изменённых
сообщений и синхронизирует их между устройствами одного владельца:
TypendruckerGram Desktop и собственным Android-клиентом (форк на базе
exteraGram, отдельный подпроект).

Главное хранилище — локальная база на каждом устройстве, хранится бессрочно.
Сервер — только обменный узел: держит зашифрованные события, пока их не
заберут остальные устройства, и не дольше 5 дней.

**Владелец** = один Telegram-аккаунт. Если в клиенте несколько аккаунтов,
у каждого свой ключ синхронизации, токены и (опционально) свой catcher.

## Подпроекты и порядок

1. **Протокол + сервер** (relay и catcher) — эта спека.
2. **Desktop** — эта спека.
3. **Android** — отдельная спека. Сначала выбрать открытый, живой форк
   exteraGram, затем подключить тот же протокол.

## Что уже есть в AyuGram Desktop

- `Telegram/SourceFiles/ayu/data/` — SQLite `tdata/ayudata.db`, таблицы
  `DeletedMessage` и `EditedMessage`.
- Запись правки: `data/data_session.cpp` → `AyuMessages::addEditedMessage`.
- Запись удаления: `ayu/utils/telegram_helpers.cpp` → `AyuMessages::addDeletedMessage`.
- Сохраняется только текст; медиа не сохраняются (`mediaPath = "/"`, todo).
- Удаление ловится, только если сообщение было загружено клиентом
  (Telegram присылает на удаление только ID).

## Архитектура

```
 Desktop (ayudata.db + ayu/sync)        Android (локальная БД + тот же протокол)
        │  HTTPS, только шифроблобы             │
        ▼                                       ▼
 Сервер tiktok-ingest (Lightsail), Caddy → https://unionofjackbox.tokenized.name/typsync/
   relay   — Python, aiohttp + SQLite: события и медиа-блобы ≤ 5 дней
   catcher — Python, Telethon-юзербот: включается, когда все устройства офлайн
```

### Кто ловит события

- **Устройства** — основной источник. Каждое пишет правки и удаления в свою
  базу, шифрует и отправляет в relay (см. «События»).
- **Catcher** — запасной. Подключается, только когда **все** устройства
  молчат больше 3 минут (по heartbeat). Когда любое устройство вернулось,
  работает ещё 2 минуты внахлёст и отключается.
  - Сообщение пришло днём, удалено ночью: catcher отправляет только
    `delete` с ID; текст уже есть на устройствах.
  - Сообщение пришло и удалено ночью: catcher сохранил его в момент
    получения как событие `message`.
- Дубли (одно событие от нескольких источников) отсеиваются по ключу
  дедупликации — на сервере и при слиянии на устройстве.

### Шифрование

- У устройств одного владельца общая пара ключей X25519 («ключ синхронизации»).
  Её генерирует первое устройство. Остальные получают её при сопряжении:
  QR-код или код из 3 групп по 4 символа, действует 10 минут,
  передаётся через relay в зашифрованном виде
  (ключ шифрования выводится из кода через HKDF-SHA256).
- Шифрование события: эфемерный X25519 → общий секрет → HKDF-SHA256 →
  AES-256-GCM. Формат блоба:
  `version(1) | ephemeral_pub(32) | nonce(12) | ciphertext | tag(16)`.
- Catcher знает **только открытый ключ**: может шифровать, не может читать
  то, что лежит в relay. Открытый текст у него существует только в памяти
  в момент получения сообщения.
- Реализации: OpenSSL (Desktop), BouncyCastle/JCA (Android), `cryptography`
  (Python). Новых зависимостей в Desktop нет.
- Сервер видит: какое устройство какого владельца положило блоб, его размер
  и ключ дедупликации. Текста, имён чатов и авторов не видит.

### Риск catcher

На сервере лежит Telegram-сессия аккаунта. Взлом сервера = доступ к
аккаунту (но не к старым событиям — они зашифрованы). Меры:
- файл сессии читается только системным пользователем catcher (не root);
- catcher можно выключить в настройках синхронизации и завершить его сессию
  в «Устройствах» Telegram;
- сервер уже за UFW + Fail2ban.

## События

Открытый вид (JSON до шифрования):

**Снимок** (`snapshot`) — содержимое одной версии сообщения:
`dialog`, `topic`, `msgId`, `fromId`, `date`, `editDate`, `text`, `entities`,
`reply`, `groupedId`, `media?`.

| Тип | Кто шлёт | Поля |
|---|---|---|
| `message` | только catcher | `account`, `snapshot` — сообщение, пришедшее ночью |
| `edit` | устройства и catcher | `account`, `previous` — снимок **заменённой** версии (то, что пишется в `EditedMessage`), `newEditDate` |
| `delete` | устройства и catcher | `account`, `dialog?` (для каналов и супергрупп), `msgIds[]`, `snapshots[]` — снимки, если источник их знал, `date` |

Почему так: устройство, которое было офлайн, никогда не видело старую версию
или удалённый текст — поэтому событие везёт снимок с собой. Новую версию
сообщения устройство и так получит от Telegram. Днём устройства не пересылают
друг другу каждое входящее сообщение — оба получают его от Telegram сами;
это экономит место на сервере.

Catcher, у которого нет снимка (сообщение пришло днём), шлёт `delete` с пустым
`snapshots` — устройства достанут текст из своего `CachedMessage`.

`media` — `{ blobId, mime, size, name, kind }`; сам файл — отдельный
зашифрованный блоб.

Ключ дедупликации: `sha256(account | dialog | msgId | editDate | type)`
в hex. Для `delete` — по каждому ID.

## Relay

Python 3.12, aiohttp, SQLite, systemd-сервис на `127.0.0.1:8090`, за Caddy
по пути `/typsync/*` существующего домена (без новой DNS-записи). Токен устройства — 32 случайных байта, на сервере хранится
только его sha256.

| Метод | Назначение |
|---|---|
| `POST /v1/owners` | создать владельца (первое устройство), выдать токен |
| `POST /v1/pair/start`, `POST /v1/pair/claim` | сопряжение нового устройства по коду |
| `POST /v1/events` | пачка событий (до 500 шт / 2 МБ), дедуп по ключу |
| `GET /v1/events?after=<cursor>&limit=` | новые события, кроме своих |
| `PUT /v1/blobs/{id}`, `GET /v1/blobs/{id}` | медиа-блобы |
| `POST /v1/heartbeat` | «я онлайн» раз в минуту; управляет catcher |
| `GET /v1/status` | квоты, последнее время онлайна устройств, catcher вкл/выкл |
| `DELETE /v1/devices/{id}` | отвязать устройство |
| `PUT /v1/settings` | несекретные настройки владельца: лимит медиа для catcher, catcher вкл/выкл |

### Экономия места на сервере

- Всё старше **5 дней** удаляется раз в час.
- Событие и блоб удаляются раньше, если их уже забрали **все** устройства
  владельца (сервисное устройство catcher не считается получателем).
- Квота на владельца: **1 ГБ** суммарно (по умолчанию, настраивается в конфиге
  сервера). При превышении сначала удаляются самые старые медиа-блобы, затем
  события; устройство получает в ответе флаг `trimmed`.
- Максимальный размер одного блоба на сервере — **50 МБ**, независимо от
  настроек клиента.
- Ограничение частоты запросов на токен.

## Catcher

Python 3.12, Telethon, отдельный systemd-сервис.

- Раз в 30 секунд опрашивает relay (локально), есть ли онлайн-устройства.
- Подключается при «все офлайн > 3 мин», отключается через 2 минуты после
  возвращения любого устройства.
- Новое сообщение → событие `message` (медиа до лимита из настроек
  владельца в relay скачиваются и шифруются блобом).
- Правка → `edit`, удаление → `delete`.
- Шифрует открытым ключом владельца и отправляет в relay по HTTP на
  `127.0.0.1` со своим сервисным токеном (как отдельное «устройство» без
  права читать события).
- Первый вход в Telegram — разовый CLI-скрипт на сервере (номер, код, 2FA).

## Desktop

Новый модуль `Telegram/SourceFiles/ayu/sync/`:

| Файл | Ответственность |
|---|---|
| `sync_crypto` | ключи, шифрование/расшифровка блобов, коды сопряжения (OpenSSL) |
| `sync_client` | HTTP, очередь отправки, pull по курсору, heartbeat, повторы с backoff |
| `sync_events` | сериализация `message`/`edit`/`delete` ⇄ JSON |
| `sync_merge` | применение чужих событий к локальной базе с дедупом |
| `sync_settings` UI | раздел «Синхронизация» в настройках TypendruckerGram |

Изменения в существующем коде:

- **Локальный кеш сообщений** — новая таблица `CachedMessage` в
  `ayudata.db`: текст, entities и метаданные каждого полученного сообщения.
  **Хранится бессрочно.** Нужен, чтобы восстановить удалённое, даже если оно
  не было загружено в открытый чат, и чтобы применять ночные `delete` от catcher.
- **Медиа** — доделать `todo` в `messages_storage.cpp`: медиа удалённых и
  изменённых сообщений до лимита сохраняются в `tdata/ayu_media/` и
  показываются в истории удалённых.
- Хуки `addEditedMessage` / `addDeletedMessage` и приём новых сообщений
  дополнительно кладут событие в очередь отправки.
- Чужое `delete` по сообщению из кеша создаёт запись в `DeletedMessage`;
  чужое `edit` — запись в `EditedMessage`.

Настройки «Синхронизация»:
- вкл/выкл; адрес сервера;
- «Создать ключ» (первое устройство) / «Подключить устройство» (QR + код) /
  «Ввести код»;
- **лимит сохранения медиа на файл** — задаёт пользователь, рекомендовано
  **20 МБ** (подпись «рекомендуется»); 0 — только текст;
- статус: последняя синхронизация, очередь, catcher вкл/выкл, квота сервера;
- список устройств с кнопкой «Отвязать».

## Ошибки

- Нет сети / сервер недоступен: события копятся в локальной очереди
  (`SyncOutbox` в `ayudata.db`), отправляются при восстановлении.
- Блоб не расшифровывается или JSON битый: событие пропускается, пишется в лог.
- Устройство не выходило на связь больше 5 дней: получает всё, что осталось,
  и предупреждение «возможны пропуски за период …».
- Сервер вернул `trimmed`: показать предупреждение в статусе.
- Конфликтов нет: события только добавляются, слияние по ключу дедупликации
  идемпотентно.

## Тестирование

- Python: pytest для relay (API, дедуп, срок хранения, квоты, удаление после
  доставки всем) и для шифрования; тестовые векторы шифрования — общий
  JSON-файл, который проверяют и Python, и C++.
- Desktop: сборка через GitHub Actions; ручная проверка на двух копиях
  клиента (portable) с одним сервером: правка, удаление, сопряжение,
  офлайн-очередь, ночной сценарий с catcher.
- Catcher: прогон на тестовом аккаунте до подключения основного.

## Вне рамок

- Android-клиент (отдельная спека).
- Синхронизация чего-либо, кроме удалённых/изменённых сообщений и кеша
  сообщений (настройки, фильтры и т.п.).
- Восстановление ключа синхронизации при потере всех устройств: без ключа
  данные на сервере нечитаемы, а через 5 дней всё равно удаляются.
